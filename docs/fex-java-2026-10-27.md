# FEX signal return and Java compilation, 2026-10-27

Release qualification found an intermittent amd64 Temurin 21 crash that a single image-matrix
run had missed. The same digest failed once in 40 runs with both the 0.3.4 host candidate and
the published 0.3.3 host, using the original `fex-2610-dmx8` guest. QEMU passed 20/20. Failures
were SIGILL or SIGSEGV around C1-compiled method entries during `javac`. The maintainer chose
to address this before releasing 0.3.4.

## Changes

`fex-2610-dmx9` keeps the same pinned upstream source and existing dmx patches and adds two
changes in [build-fex.py](../scripts/build-fex.py):

- Restore `InSyscallInfo` on every signal return, including a handler that leaves RIP unchanged.
  Otherwise a later signal can use a stale saved stack pointer and overwrite live stack data.
  This matches the defect described in [FEX issue 5901](https://github.com/FEX-Emu/FEX/issues/5901).
  The standalone x86 fixture in `scripts/fixtures/signal-frame-x86_64.S` varies stack depth while
  timer signals arrive and checks the stack contents. It failed in all three runs with the old
  emulator and passed in all three with the signal fix and all three with QEMU. `make x86test`
  now runs the fixture three times per emulator and requires actual signal delivery.
- Read each aligned eight-byte code word once while decoding an instruction, and derive both
  opcode and operands from that snapshot. The old decoder read the opcode separately from a
  later operand copy, allowing an atomic rewrite between the reads to mix versions.
  [HotSpot's x86 entry patching](https://github.com/openjdk/jdk21u/blob/master/src/hotspot/cpu/x86/nativeInst_x86.cpp)
  uses an aligned eight-byte atomic store. A 15-byte x86 instruction needs at most three such
  words; executable-range checks still precede reads, and synthetic vsyscall bytes retain their
  existing path. This addresses the decoding race; it does not make arbitrary cross-word
  self-modifying code atomic.

The signal fix alone still failed one of 100 Java runs. The decoder-only candidate passed
150/150 with its live emulator hash verified. This supports the entry-rewrite diagnosis, but
is not a deterministic reproduction of that Java race. A separate tiny concurrent-entry
program passed with both old and new emulators, so it is not claimed as regression evidence.

## Controls and evidence boundaries

The same Java digest and workload are used throughout: compilation, JIT, a worker thread,
shared mmap and partial flush, with a 1 GiB container limit, two CPUs and a 4 GiB VM ceiling.
`make javatest` repeats the workload 100 times and fails if any iteration fails. The matrix
records the live interpreter hash; `--expect-emulator-sha256` rejects an unintended interpreter.
Java crash reports are retained in bounded form before removing the failed container.

Disabling FEX multiblock compilation still failed once in 100 runs. Full SMC checks repeatedly
exited 137 under the same memory limit (13 completed failures before stopping), so neither
setting was adopted. Three early experimental guests accidentally packaged the old emulator
because an imported build module's `X86_EMULATORS` dictionary had captured the old filename.
Those runs are baseline evidence only, including 99/100 and 149/150 results originally labelled
as candidates. Subsequent candidate runs checked the packaged and live emulator against the
intended sha256. The release uses the normal `make fex` / `make guest` path.

The combined production guest passed all 24 image cases and 100/100 Java repetitions. The
published 0.3.4 installer, signed VM selftest and update from 0.3.3 also passed; the update
preserved the running VM and data and loaded the verified dmx9 interpreter on the next boot.
Final release qualification and its artifact hashes are recorded in
[measurements/2026-10-27-release-0.3.4.json](measurements/2026-10-27-release-0.3.4.json).
Repeated passes are bounded local evidence, not a guarantee for every JVM, workload or schedule.
