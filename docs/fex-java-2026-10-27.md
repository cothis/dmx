# FEX signal return and Java compilation, 2026-10-27

Release qualification found an intermittent amd64 Temurin 21 crash that a single image-matrix
run had missed. The same digest failed once in 40 runs with both the 0.3.4 host candidate and
the published 0.3.3 host, using the original `fex-2610-dmx8` guest. QEMU passed 20/20. Failures
were SIGILL or SIGSEGV around C1-compiled method entries during `javac`. The maintainer chose
to address this before releasing 0.3.4.

## Changes

`fex-2610-dmx9` keeps the same pinned upstream source and existing dmx patches and adds two
changes in [build-fex.py](../scripts/build-fex.py):

- Restore `InSyscallInfo` on every signal return, including a handler that leaves RIP unchanged.
  Otherwise a later signal can use a stale saved stack pointer and overwrite live stack data.
  This matches the defect described in [FEX issue 5901](https://github.com/FEX-Emu/FEX/issues/5901).
  The standalone x86 fixture in `scripts/fixtures/signal-frame-x86_64.S` varies stack depth while
  timer signals arrive and checks the stack contents. It failed in all three runs with the old
  emulator and passed in all three with the signal fix and all three with QEMU. `make x86test`
  now runs the fixture three times per emulator and requires actual signal delivery.
- Read each aligned eight-byte code word once while decoding an instruction, and derive both
  opcode and operands from that snapshot. The old decoder read the opcode separately from a
  later operand copy, allowing an atomic rewrite between the reads to mix versions.
  [HotSpot's x86 entry patching](https://github.com/openjdk/jdk21u/blob/master/src/hotspot/cpu/x86/nativeInst_x86.cpp)
  uses an aligned eight-byte atomic store. A 15-byte x86 instruction needs at most three such
  words; executable-range checks still precede reads, and synthetic vsyscall bytes retain their
  existing path. This addresses the decoding race; it does not make arbitrary cross-word
  self-modifying code atomic.

The signal fix alone still failed one of 100 Java runs. The decoder-only candidate passed
150/150 with its live emulator hash verified. This supports the entry-rewrite diagnosis, but
is not a deterministic reproduction of that Java race. A separate tiny concurrent-entry
program passed with both old and new emulators, so it is not claimed as regression evidence
(the follow-up below explains why and replaces it).

## Controls and evidence boundaries

The same Java digest and workload are used throughout: compilation, JIT, a worker thread,
shared mmap and partial flush, with a 1 GiB container limit, two CPUs and a 4 GiB VM ceiling.
`make javatest` repeats the workload 100 times and fails if any iteration fails. The matrix
records the live interpreter hash; `--expect-emulator-sha256` rejects an unintended interpreter.
Java crash reports are retained in bounded form before removing the failed container.

Disabling FEX multiblock compilation still failed once in 100 runs. Full SMC checks repeatedly
exited 137 under the same memory limit (13 completed failures before stopping), so neither
setting was adopted. Three early experimental guests accidentally packaged the old emulator
because an imported build module's `X86_EMULATORS` dictionary had captured the old filename.
Those runs are baseline evidence only, including 99/100 and 149/150 results originally labelled
as candidates. Subsequent candidate runs checked the packaged and live emulator against the
intended sha256. The release uses the normal `make fex` / `make guest` path.

The combined production guest passed all 24 image cases and 100/100 Java repetitions. The
published 0.3.4 installer, signed VM selftest and update from 0.3.3 also passed; the update
preserved the running VM and data and loaded the verified dmx9 interpreter on the next boot.
Final release qualification and its artifact hashes are recorded in
[measurements/2026-10-27-release-0.3.4.json](measurements/2026-10-27-release-0.3.4.json).
Repeated passes are bounded local evidence, not a guarantee for every JVM, workload or schedule.

## Follow-up: cause confirmed, and a second defect (2026-10-27)

**The Java crashes were mixed decodes of HotSpot's method-entry patch.** The six distinct
crash reports (two of the seven files are byte-identical) all stop at the verified entry of a
level-3 C1 method within 5–8 ms of a C2 version of the same method being installed. That is
when HotSpot makes the C1 code not entrant by replacing the 8-byte-aligned word
`89 84 24 00 c0 fe ff 55` (stack bang, `push rbp`) with `e9 <rel32> fe ff 55`. Decoding the
first one or two bytes from the old word and the rest from the new one reproduces every
report exactly, which neither a coherent old nor a coherent new view can:

| Report | Bytes from the old word | Instruction FEX ran | Predicted | Reported |
|---|---|---|---|---|
| current-fex-14 | `89 84` | `mov [rdi+2*rax-0x1f8ba], eax` | fault at `0x2d02b3fe6` | SIGSEGV at `0x2d02b3fe6` |
| current-fex-147 | `89 84` | `mov [rbp+8*rbp-0x1f8ad], eax` | fault at `0x47fffa948d723` | SIGSEGV at `0x47fffa948d723` |
| multiblock-0-58 | `89` | `mov [rbx-0x1f8af7b], ebx` | fault at `0x7fff9507d9d5` | SIGSEGV at `0x7fff9507d9d5` |
| previous-fex-26 | `89` | `mov ebx, edi`, then `insb` | RBX = low half of RDI, #GP at +2 | RBX `0x980a9b28`, SI_KERNEL at +2 |
| current-fex-7, -27 | `89` | two 2–3 byte instructions, then `fe ff` | SIGILL at +5 | SIGILL at +5 |

`scripts/fixtures/entry-patch-x86_64.S` reproduces the race without instrumentation: one
thread keeps rewriting an aligned code word between two complete one-instruction versions
while another calls it. Twenty runs per emulator, same binary (sha256 `276462ae…`):

| Emulator | Passed | Failures |
|---|---|---|
| dmx8 (original) | 2/20 | 18 mixed decodes (11 returned 59, 7 the scratch address) |
| signal-return fix only | 2/20 | 18 mixed decodes |
| decoder fix only | 20/20 | – |
| dmx9 | 20/20 | – |
| dmx10 | 20/20 | – |
| QEMU | 20/20 | – |

So the decoder fix in dmx9 is the fix for the Java crash; the signal-return fix is a separate,
real defect with its own fixture. The earlier Java counts could not have shown this: pooled,
the old emulator failed about 4 times in 330 runs, so even 150 clean runs had a one-in-six
chance under the old failure rate. An earlier draft of the microprobe (Luna, kept locally)
missed the race because its writer held the second version for a single instruction.
Its one `entry-race-failed` came from an earlier build; that binary had no path to the string.

**A second defect: stale translations.** FEX's default SMC tracking (`mtrack`) only learns
about writes to code through write faults. It write-protects a page that has just got
translated code *after* decoding and compiling the block. A write that lands in between does
not fault, so the block keeps running the old bytes until some later write to that page
faults. `scripts/fixtures/code-stale-x86_64.S` publishes a new version, has the reader
serialize with CPUID as x86 cross-modifying code requires, and checks that the old version
no longer runs. It failed every run on dmx8 (10/10) and dmx9 (20/20 at the regression's
setting, 20/20 more across four writer delays), often still running version 0 thousands of
versions later. QEMU passed 30/30. HotSpot meets this whenever it patches an entry while
another thread translates it: a not-entrant method, or one whose code assumptions a
deoptimization just invalidated, can keep being entered. None of the six crashes is
explained by it, but it is wrong code and dmx10 fixes it.

`fex-2610-dmx10` adds that fix. While decoding, it records every aligned word it read from
code that may change, meaning a writable mapping or a shared one that may have a writable
alias. Once the block compiles, it write-protects all of the block's pages, including pages
another thread marked but may not yet have protected, and compares the words with memory.
If they differ it decodes again. A write after the protection faults and waits on
`CodeInvalidationMutex`, which the compiling thread holds shared, so the comparison sees
stable memory. Protection cannot stop writes from another process sharing the memory.
After eight changed attempts the block runs once and is not cached. A Sonnet review of the
first version found the shared-alias gap, the stale block being cached at the retry cap and
side effects before the check; all three were fixed before the production build.
The cost per compile of writable code is a page-table call per page and a comparison.
Javac's median time did not change: 2.09 s for dmx9 and the candidate, 2.08 s for dmx10 (100 runs each).
A JIT-style compile storm did show it, though: 262,144 new blocks took 318–324 ms with dmx10
against 268–270 ms with dmx9 (`scripts/fixtures/compile-storm-x86_64.S`). dmx10 protected pages
that were already protected again on every compile. `fex-2610-dmx11` remembers the pages it
protected until their next invalidation; every change that makes a page writable again runs one
under `CodeInvalidationMutex`. With that, the storm takes 248–259 ms. dmx11 passed both fixtures (20/20 each),
every suite and Java 100/100; it ships in v0.3.5.
