## Changes since 0.3.8

A fix for guest networking that could stop for good right after the VM started.

- **The guest no longer loses its network after a fresh start.** In about one VM start in a
  hundred, the guest stopped receiving anything during its first large download. DNS to every
  server and every TCP connection then timed out until the VM was restarted, while sending still
  worked. The cause was a deadlock with Linux's virtio-net driver. dmx sent 64 KB frames (MTU 65520)
  in order, but the driver adds receive buffers only after it has received something. It refills
  its 64-slot ring only once more than 32 slots are empty, so as little as 32 buffers of
  1536 bytes can stay posted, and a 64 KB frame then never fits. The MTU is now 49126, the
  largest whose frame always fits what Linux keeps posted. A frame over it is dropped rather
  than left blocking everything behind it. Fresh starts with a 1 MiB download each: 0.3.8 stalled
  3 times in 300, this release 0 times in 900. Host-to-guest throughput is within a few percent of
  before (440–467 MB/s for 64 MB), and memory use is unchanged.

If a VM started by an earlier version loses its network, `dmx stop` and use it again; after
updating, the next start runs the fixed version.

Qualification passed 61 unit tests, 23 VM selftests (idle 97 MiB), 58 daemon checks, 33 MCP
checks, 53 x86 checks, 69 Docker checks, 44 sandbox checks, all 24 digest-pinned image cases and
the 100-run Java gate. The guest is unchanged from 0.3.8.
