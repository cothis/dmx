## Changes since 0.4.1

- Name lookups work on networks that never answer IPv6 (AAAA) DNS queries. dmx used to answer
  such a query with a failure after 5 s, and programs built on musl, including a static `uv`, then
  failed the whole lookup with `Try again` even though the name had an IPv4 address. Once a
  name's IPv4 lookup has found an address, its AAAA lookup now ends within 300 ms as "no records".
  Reproduced with a record whose AAAA never answers: `uv` in a container, on a user network and in
  `docker build` went from `Try again` after 5 s to resolving in about 0.4 s. The fix has not yet
  run on the network where the failure was first reported.
- macOS's local network permission is now visible. An engine started by launchd (`dmx install`)
  cannot reach LAN addresses until the Mac's owner allows it, and `.local` names may not resolve; the
  public internet is not affected. macOS's prompt now says why dmx asks, it appears when the VM starts
  rather than at the first failed connection, and `dmx status`, `dmx doctor` and the daemon log say
  when access is blocked. The new `make localnettest` checks this under a real launchd job. The
  allowed state of a launchd engine has not been tested, because answering the prompt takes the owner.

Known issue, not new in this release: `linux/amd64` images can crash at random under FEX, more often
when the Mac is busy. It was measured on `postgres:18-alpine`'s start-up, which exits 139 or with a Go
runtime error from `gosu`. Over 135 runs each, 0.4.1 failed 17 and 0.4.2 failed 25; in
the fairer half, alternating in short blocks with a load of 3 to 6, 0.4.1 failed 5 of 60 and 0.4.2 none
of 60, and `linux/arm64` failed none of 30. The guest and emulator are the same bytes in both. The cause
is not known yet; a new run usually succeeds. The qemu emulator (`x86_emulator`) was not compared.

The guest is byte-identical to 0.4.1, so updating does not download it again.
