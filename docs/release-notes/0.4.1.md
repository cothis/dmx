## Changes since 0.4.0

- Bound daemon, VM console and guest dockerd diagnostic streams: each keeps at most three
  1 MiB files. Oversized old logs are trimmed on startup; legacy launchd log descriptors are
  detached before rotation. Output does not accumulate in an in-memory queue.
- New containers default to json-file logging with `max-size: "10m"` and `max-file: "2"`.
  Explicit daemon/per-container choices are preserved. Existing containers retain their old
  logging settings; recreate them with the desired options to change those settings.
- Guest startup diagnostics retain only an 8 KiB error tail. A collector's lifetime follows
  dockerd instead of its inherited pipes, so a surviving descendant cannot keep the log lock
  and block Docker restart after a failed start or crash. Timed-out starts are killed/reaped.
- Log setup failures no longer block engine/Docker startup: unusable sinks are disabled,
  host warnings appear in `dmx status`, and output is drained with bounded memory.

Images, volumes, writable layers and build caches remain user data; this change does not
impose a global disk quota or remove existing containers. Usable host and guest diagnostic
streams together use at most 9 MiB of file contents, plus filesystem metadata. Inaccessible
or unsafe old files are left alone. See `docs/docker.md` for details.

If the guest agent itself crashes while dockerd survives, Docker continues but diagnostic
output requires a VM restart to resume; container logs are independent of this limitation.

unit97, real-VM storage64 (four guest Rust tests), selftest23, daemon58, MCP33, menu25 plus
typedVM, app14 plus typed installation. Earlier compatibility matrix: x8653, Docker69,
sandbox44, images24, Java100. Unchanged normal-path payloads and final error/recovery checks
are recorded separately in `docs/measurements/2026-10-30-storage.json`.
