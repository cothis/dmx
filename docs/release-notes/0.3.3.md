## Changes since 0.3.2

Two other models reviewed 0.3.2's `dmx update` adversarially and found what this fixes. Updating
from 0.3.2 is worth doing: two of these are security defects in that release.

- **The downloaded binary is no longer run before its signature is checked.** 0.3.2 read the
  version out of it by executing it, and only then compared the Developer ID. A release server
  that served a binary with a matching sha256 therefore got code execution as the user, and the
  rejection came too late. The signature check now runs first, and it is a `codesign` requirement
  tied to Apple's anchor and the team rather than a comparison of the team string.
- **An update no longer stops a VM that is booting.** 0.3.2 asked an "idle" daemon to quit, but
  treated `starting`, `stopping` and a failed status call as idle, and quitting powers the VM off
  with its containers. `dmx update` now never asks a daemon to quit: a daemon whose VM is off
  exits ten seconds after its last client anyway, and the report says so.
- **The archive's `dmx` has to be a plain file.** A symlink named `dmx` pointing at the binary
  being replaced would have passed the version and signature checks — they would have read the
  old binary — and the install would have replaced it with a link to itself.
- **`--version` is validated**, since it reaches a URL, a directory name and a removal; two
  updates running at once no longer share a work directory, so one cannot install what the other
  has not finished checking; and an update with no version named refuses to go backwards (a dmx
  newer than the newest release is not replaced by it).
- **`release.json` is written atomically.** A truncated receipt makes a downloaded guest look
  locally built, which dmx never replaces, so the guest would have stayed behind the binary.
- **FEX reads nothing from the caller's `$HOME` for a setuid x86 program.** The `AT_SECURE`
  hardening in 0.3.0 covered the configuration layers, but FEX's config, data and cache
  directories are derived from `$HOME` and `XDG_*` and were still used for the thunk database.
  They now answer with the system-wide path.
- **The address-space probe stops instead of looping.** Without `/proc` and under an `RLIMIT_AS`
  every mapping fails with ENOMEM; the probe used to halve the range anyway, which is 68 billion
  calls for 128 TiB. Only EEXIST splits now; anything else makes FEX say it cannot reserve the
  space and stop.
- Smaller defects from the same reviews: a codesign that cannot start no longer ends dmx (the
  process was waited on without checking that it launched); the published `.sha256` is accepted
  whether it holds the digest alone or in uppercase; the archive member is rejected before its
  mode is changed, not after; the copy that gets installed is re-hashed just before the rename;
  two errors gained the hint the project's rules require; and `dmx doctor` reports a daemon that
  speaks another protocol instead of dropping the check.
- The refusal to run with an unreserved address space is scoped to the probe path. With `/proc`
  readable an empty result is the host's own answer, and FEX runs with its allocator as it always
  has.
- Checks that could pass while broken now fail: x86test confirms its `umount /proc` worked and has
  one setuid control per configuration source (the environment layer wins over
  `$HOME/.fex-emu/Config.json`, so the old single control proved only half of it), the signature
  decision has a test per combination of what the two binaries carry, and the image matrix refuses
  an explicit image/platform pair that has no pins instead of passing with nothing run.
