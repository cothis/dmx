## Changes since 0.4.6

- The guest clock now follows the Mac's. The guest's counter stands still while the Mac sleeps (a locked Mac soon does), and dmx set the guest clock only at boot and before `dmx exec`, so after the Mac woke up, containers saw the old time until the VM restarted. A change of the Mac's clock by macOS was not followed either. The daemon now looks every 15 s, before each Docker, port or exec connection, and before a container start or exec on a Docker connection kept open: after the Mac slept or its clock moved, it sets the guest clock at once. Once a minute it also corrects drift, slewing offsets under 128 ms as NTP clients do, so a periodic correction never sets the clock back. It measures the offset before changing anything and moves the clock relative to the guest's own time, so a correction that waits behind other work in the guest does not carry a stale time.

Measured on the real VM: a guest clock set an hour back was corrected within 61 s; a guest 50 ms ahead was slewed back at 0.5 ms/s with CLOCK_REALTIME never going backwards (0.0 ms), where 0.4.6 stepped it back 48.7 ms; with the guest agent paused for 1.5 s at a time for 94 s, nothing went back (0.0 ms; an earlier draft of this fix went back 188 ms). While testing, macOS moved this Mac's clock back by 2.05 s and, an hour later, 1.86 s after NTP answers: a 0.4.6 VM stayed 2,070 ms ahead, while the new daemon moved the guest with the host within 15 s. A real sleep was not exercised; it is recognized from the Mac's clocks (unit tests).

The guest's agent changed, so updating downloads the guest once more (63 MB). The kernel and the Docker image are unchanged.

Reviewed by Claude Sonnet 5.5 and Codex; their findings (a stale timestamp in a queued correction, Docker connections kept open, a failing guest delaying requests, overcorrection from a slow measurement) are fixed and reproduced where they could be.
